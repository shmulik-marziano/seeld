# תכנון: אימות לקוחות API (מפתחות)

סטטוס: תכנון בלבד. אין פריסה, אין טבלה חיה. הסכמה המוצעת: `supabase/proposed/01_api_clients.sql`.

## עקרונות
- מפתח הוא מחרוזת אקראית של 32 בתים (base64url) עם קידומת קריאה: `sk_live_<prefix8>_<secret>`.
- המפתח מוצג פעם אחת ביצירה. במסד נשמר רק `sha256` שלו (`key_hash`) ו-8 תווי קידומת (`key_prefix`) לחיפוש ולתצוגה.
- השוואה בזמן קבוע (`timingSafeEqual`) אחרי חיפוש לפי הקידומת.
- לכל לקוח: `scopes` (למשל `documents:read`), `rate_limit_per_min`, `status`, `expires_at`.
- ביטול = `status='revoked'` + `revoked_at`. אין מחיקה.
- כל יצירה, ביטול ושימוש חריג נרשמים ב-`audit_log` (בלי המפתח, בלי PII).

## זרימה בבקשה
1. כותרת `x-api-key` נקראת ב-`_shared/auth.ts` (`verifyApiKey`).
2. חיפוש לפי `key_prefix` בטבלה (שירות בלבד, service role), השוואת hash, בדיקת `status`/`expires_at`.
3. `requireScope` על ה-route. חוסר הרשאה: 403.
4. מגבלת קצב לפי `client:<id>` דרך `consume_rate_limit` (הצעה 03). חריגה: 429 + `retry-after`.
5. עדכון `last_used_at` (לכל היותר פעם בדקה, לא בכל בקשה).

## הפרדה מגולשי אתר
- מפתחות API הם שרת-לשרת בלבד. אסור להטמיע בקוד דפדפן.
- משתמשי קצה ממשיכים להזדהות עם JWT של Supabase. סוכנים נדרשים ל-aal2 (TOTP).

## החלטות פתוחות לבעלים
- האם לקוח API שייך לסוכנות (`agency_id`) או ברמת הפלטפורמה.
- רוטציה: חלון חפיפה של שני מפתחות פעילים ללקוח (מומלץ: כן).
